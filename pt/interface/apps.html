Apps ​

Um App é uma tela web construída dentro da plataforma: formulário, painel, consulta. Ele tem endereço próprio, roda num processo separado e pode ser aberto por quem não é usuário do ProAgentHub.

É a resposta para "e quando quem vai usar não deveria entrar no ProAgentHub?".

Aba Geral ​

Descrição, ícone (com o qual ele aparece no menu) e o slug — o pedaço final do endereço, /a/<slug>.

O modo de acesso decide quem entra:

  • Interno — exige usuário conectado, e respeita os grupos.
  • Público — qualquer pessoa com o link abre, sem login.

Público é público mesmo

Num App público não existe usuário conectado: o código da página não tem quem identificar, e tudo o que ele expõe fica ao alcance de quem tiver o endereço. Não coloque atrás de um App público nada que você não publicaria numa página aberta.

Aba Global ​

CSS, JavaScript e um backend global compartilhados por todas as páginas. É onde ficam o tema, os utilitários e as funções que várias páginas chamam.

Aba Páginas ​

Cada página declara como é feita, e isso é uma escolha por página:

  • Visual — montada arrastando componentes no designer. O HTML é gerado a partir da árvore.
  • Código — HTML escrito à mão.

Não há sincronia de volta

Do visual sai HTML; do HTML não se remonta a árvore automaticamente. Existe uma importação de código→visual, mas é um passo único que você aciona de propósito, não um espelho. CSS e JS continuam editáveis à mão nos dois modos — é a saída de emergência para o que o designer não cobre.

O backend da página ​

Cada página tem uma aba de Python. Toda função de topo cujo nome não comece com _ vira um endpoint, chamável do JavaScript da página com proApp.call('nome', {…}).

Não há rota nem decorador: a assinatura é o contrato. A mesma leitura do código que monta a lista de funções na tela valida os argumentos que chegam — por isso as duas não têm como divergir.

Estado de módulo não sobrevive entre chamadas

O escopo é remontado a cada requisição, porque carrega o usuário conectado. Uma variável global não guarda nada de uma chamada para a outra. O que precisa persistir vai para db.

Os dados do App ​

Cada App tem um banco MongoDB só dele, app_<id> — pelo número, não pelo slug, de modo que renomear o App nunca move os dados.

O código chega nele pelo db injetado ou pelas mesmas operações soltas no escopo (save, find, delete…). Não há conexão para abrir, nem como endereçar o banco de outro App. Ver Backend de página.

O banco é apagado junto com o App.

Arquivos enviados pela página ​

Arraste o componente Arquivo para dentro de um formulário e dê um nome a ele — esse nome vira o parâmetro da função de backend, como em qualquer outro campo.

Ao clicar no botão que chama a função, a página envia o arquivo primeiro e passa ao Python o identificador dele. No backend:

python
def receber(anexo: str) -> str:
    dados = read_upload(anexo)          # os bytes
    info = upload_info(anexo)           # nome, tipo, tamanho, quem enviou
    return f"Recebi {info['filename']} com {len(dados)} bytes"

Marcando Vários arquivos, o parâmetro chega como uma lista de identificadores.

Os arquivos ficam no mesmo banco do App, ao lado dos dados dele — e valem as mesmas regras: não há como alcançar o arquivo de outro App, eles somem junto com o App, e não viajam na exportação (que leva a estrutura, não os dados de produção). O tamanho máximo é o da plataforma, em PRO_AI_MAX_FILE_SIZE.

Para listar ou apagar: list_uploads() e delete_upload(id). Para oferecer o arquivo de volta na tela, proApp.fileLink(id) devolve o endereço de download.

Em App público, o link de download só serve a quem enviou

Num App interno vale a mesma fronteira dos dados: quem pode abrir o App pode baixar os arquivos dele. Num App público, não — o link só entrega o arquivo a quem o enviou estando autenticado, e o que um visitante anônimo envia não sai por esse endereço de forma alguma. Sem isso, um formulário público que recebe documento pessoal entregaria o documento de um visitante a qualquer outro: o identificador do arquivo é sequencial o bastante para ser adivinhado.

Para mostrar esse conteúdo mesmo assim, faça-o pelo backend da página — read_upload(id) devolve os bytes, e ali é você quem decide quem vê o quê.

Em App público o envio também tem cota por visitante (por padrão, 10 arquivos ou 100 MB a cada 10 minutos). Quem passar disso recebe um aviso para tentar mais tarde: é a única porta da plataforma em que alguém sem cadastro escreve no banco, e sem cota um único visitante encheria o disco da instalação.

A contagem é feita na memória de cada réplica do serviço que publica os Apps, e a instalação padrão sobe duas: o teto que a instalação entrega é o dobro do número configurado. Se o limite precisar ser exato, suba uma réplica só ou aperte o valor.

Aba Prévia ​

Roda o App como ele vai ficar, inclusive com o conteúdo ainda não salvo. É o mesmo renderizador que serve o App publicado, então o que você vê é o que vai sair.

A prévia roda dentro de um iframe isolado, sem acesso à origem do hub — o JavaScript que você escreve não enxerga a sessão de quem está construindo.

Aba Versões e publicação ​

Uma versão é o retrato do App inteiro — cabeçalho e todas as páginas. Publicar congela uma dessas versões, e é ela que responde em /a/<slug>.

Editar o rascunho não muda o que está no ar. Só publicar de novo muda. É o que permite mexer com calma numa tela em uso.

Onde os Apps aparecem ​

Para quem usa, um App publicado é um item do menu lateral, e não uma linha numa tela de listagem. Quem constrói vê a lista em Apps; quem consome vê só o nome e o ícone que você deu.
