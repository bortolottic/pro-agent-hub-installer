Workflows ​

A workflow is an automation: a sequence of steps the platform runs on its own — manually, on a schedule, or called from somewhere else.

There are two types, chosen by a pair of buttons on the General tab:

  • Low-code — a flow drawn as connected boxes.
  • High-code — a Python file.

The type can be switched at any time, and both contents are kept: turning it into high-code does not erase the drawn flow, and going back to low-code does not erase the code. What changes is which of the two the platform runs — and which tab you see.

The co-pilot writes both

The Pegasus button, on the General tab, takes a request in plain language and returns either a flow or the Python — and the platform recognises which came back, switches the type and drops the result on the right tab. It is the shortest path out of a blank screen, and also the way to ask "turn this flow into code".

General tab ​

Description, group and the schedule.

The schedule is a cron expression, evaluated in UTC. The screen shows the upcoming runs computed from the expression — check them there before saving; it is faster than finding out the next day that the time was off.

A scheduled workflow never overlaps itself

If the time comes round and the previous run is still going, the trigger is skipped, and recorded as such. That is the guarantee that a scheduled process never runs twice at once. Manual runs have no such lock.

The log level decides how much a run records: errors only, progress, or everything. A detailed log helps you debug and weighs on the database — old runs are pruned by the retention configured in Settings.

Flow tab (low-code) ​

The canvas where the flow is built. Drag nodes from the palette, wire outputs to inputs, and click a node to configure it.

The node types cover input and output, condition, loop, calling an agent, team or planner, data and system operations, and a script node for whatever does not fit the rest.

Live execution. When you run it from the test button, the canvas follows along:

  • the running node pulses, with a highlighted border;
  • when it finishes it changes colour according to the result and shows how long it took;
  • the ones that have not run yet stay dimmed.

This happens during the run, node by node, not only at the end. On a long flow, it is how you see where it is stuck.

Code tab (high-code) ​

A Python editor with autocomplete for the platform functions — type db_ and the list appears, with the signature and the description of each one.

The code runs with a scope already assembled: context (what came in), log(), is_cancelled() and the data, system and integration operations. No import is needed to use them. The full reference is in Workflow high-code.

A long workflow should check for cancellation

Cancellation is cooperative: the platform records the request, and it is your code that decides to stop. In a long loop, call is_cancelled() each time round and bail out when it returns true. Without that, cancelling only takes effect when the run ends by itself.

Executions tab ​

The history of that workflow, with status, duration and the log of each run.

Versions tab ​

Every save keeps a version of the workflow. The tab lists the versions, lets you compare two (in high-code, with a line-by-line diff) and restore an earlier one.

Restoring erases nothing: it creates a new version holding the old content. The way back is never lost.

Executions ​

A screen of its own, under Main: the monitor for every run on the platform, not just one workflow's.

The filter is by workflow description, status and period. While there is an active run, the list refreshes itself every few seconds — and an indicator at the top shows it is following along.

The statuses are:

StatusWhat it means
RunningGoing right now.
CompletedFinished with no error.
FailedFinished with an exception. The message is in the detail.
CancellingCancellation requested; waiting for the process to reach a stopping point.
CancelledStopped at the user's request.
AbandonedThe process running it stopped responding.

Abandoned deserves attention: it is not an error in your workflow, it is the process that died (container restarted, machine brought down). The platform marks it that way when a run stops showing signs of life for a few minutes, so no record stays stuck at "running" forever.

The detail shows the origin (manual, scheduled, webhook or API), who triggered it, the duration, the current node, a preview of the output and the full log.

Cancelling ​

The cancel button works even when the run was triggered by the scheduler, in another process — the request is written to the database and the process running it reads that within seconds.

In low-code, cancellation is checked between one node and the next: a node that has already started finishes. In high-code, it depends on your is_cancelled().
