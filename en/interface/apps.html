Apps ​

An App is a web screen built inside the platform: a form, a dashboard, a lookup. It has an address of its own, runs in a separate process and can be opened by people who are not ProAgentHub users.

It is the answer to "what if the people who will use this shouldn't be signing into ProAgentHub?".

General tab ​

Description, icon (how it appears in the menu) and the slug — the last part of the address, /a/<slug>.

The access mode decides who gets in:

  • Internal — requires a signed-in user, and respects groups.
  • Public — anyone with the link opens it, with no login.

Public means public

In a public App there is no signed-in user: the page's code has nobody to identify, and everything it exposes is within reach of whoever has the address. Do not put anything behind a public App that you would not publish on an open page.

Global tab ​

CSS, JavaScript and a global backend shared by every page. This is where the theme, the utilities and the functions several pages call all live.

Pages tab ​

Each page declares how it is made, and that is a per-page choice:

  • Visual — assembled by dragging components in the designer. The HTML is generated from the tree.
  • Code — HTML written by hand.

There is no sync back

Visual produces HTML; HTML is not turned back into a tree automatically. There is a code→visual import, but it is a one-off step you trigger on purpose, not a mirror. CSS and JS stay hand-editable in both modes — that is the escape hatch for whatever the designer does not cover.

The page backend ​

Each page has a Python tab. Every top-level function whose name does not start with _ becomes an endpoint, callable from the page's JavaScript with proApp.call('name', {…}).

There is no route and no decorator: the signature is the contract. The same reading of the code that builds the function list on screen validates the arguments that arrive — which is why the two cannot drift apart.

Module state does not survive between calls

The scope is rebuilt on every request, because it carries the signed-in user. A global variable holds nothing from one call to the next. Whatever must persist goes into db.

The App's data ​

Each App has a MongoDB database of its own, app_<id> — by the number, not the slug, so renaming an App never moves its data.

Code reaches it through the injected db or through the same operations loose in the scope (save, find, delete…). There is no connection to open, and no way to address another App's database. See Page backend.

The database is dropped along with the App.

Preview tab ​

Runs the App as it will look, including content you have not saved yet. It is the same renderer that serves the published App, so what you see is what will ship.

The preview runs inside an isolated iframe, with no access to the hub's origin — the JavaScript you write cannot see the session of whoever is building it.

Versions tab and publishing ​

A version is a snapshot of the whole App — the header and every page. Publishing freezes one of those versions, and that is what answers at /a/<slug>.

Editing the draft does not change what is live. Only publishing again does. That is what lets you work calmly on a screen that is in use.

Where Apps show up ​

To the people using it, a published App is an item on the side menu, not a row in a listing screen. Whoever builds sees the list under Apps; whoever consumes sees only the name and the icon you gave it.
