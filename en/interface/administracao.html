On this page

Administration ​

Everything on this page is visible to master users only.

Groups ​

A group is the platform's unit of access. It gathers users on one side and releases resources on the other: agents, teams, workflows, planners, MCP services and Apps.

Each release has a mode:

  • Read — open and run.
  • Write — open, run and save.

A user can be in several groups; they see the union of what their groups released, with the most permissive mode among them.

A user with no group sees nothing

And that is the correct behaviour, not a defect. Whoever signs up through the create-account screen arrives with no group at all, and depends on a master to start using anything.

Users ​

Name, e-mail, phone, password and two switches that decide a great deal:

Master — sees everything and administers everything, with no group involved. Master is not "power user": it is whoever can read an API key, change settings and export the database. Hand it out sparingly.

Disabled — the user can no longer sign in, but still exists, and with them the history of runs and conversations. That is what you use when someone leaves the company; deleting would erase the trail.

Settings ​

E-mail ​

The SMTP the platform uses for "forgot my password" and for the usage alerts. Until it is configured, neither of those goes out at all.

Licence ​

Serial and control number of the installation.

Environment variables ​

Name/value pairs available to the code of workflows, planners, MCP tools and App backends. This is where keys and addresses live that you do not want written in the middle of the code — and that differ from one environment to another.

Security ​

Workflow API token — the secret that authenticates whoever triggers a workflow from outside the platform.

Pegasus — the built-in co-pilot. On, it appears in the code and data-source screens, suggesting Python, flows and CSS selectors. It requires a chosen model; without one, the platform refuses to save it enabled.

Retention ​

How much run history to keep. Three limits, applied by a periodic cleanup:

LimitDefaultWhat it does
Execution days30Removes runs older than that.
Log days7Removes the detailed log, keeping the run header.
Executions per workflow200Trims the excess of a workflow that runs a lot.

The first two go well together: you still see that a run from 20 days ago happened and how long it took, without carrying its log line by line.

Runs still in progress are never pruned, however old they are.

The default log level for new workflows also lives here.

Token usage ​

How much each model consumed, in tokens and in cost, with a daily and a monthly report.

Cost depends on the price on the model's record. With no price, you get a token count and no figure — which is already enough to find the agent that is spending too much.

The alert and the blocking cap are configured on the model's record, not here. See Providers and models.

Import and export ​

Copies records between environments — from development to production, or from one installation to another.

The selection is a tree: pick whole groups (Workflows, Agents, Providers…) or specific records inside each one.

Dependencies come along ​

An agent without its model does not work. So, on export (and on import), the records your selection depends on are included even if you do not tick them — unless you turn the option off. Ticking a workflow brings the agent it calls, that agent's model and that model's provider.

Before you confirm, the screen shows what was added by dependency.

On import ​

What already exists at the destination is recognised by description, not by ID. An existing record is kept as it is, and the links point at it — the IDs from the file are remapped to the destination's.

That means re-importing does not undo a change made by hand at the destination. It is deliberate: importing is for bringing over what is missing, not for overwriting the environment.

Groups and users deserve attention

Bringing groups and users from another environment rewrites who has access to what. The screen flags those groups and asks for confirmation — read the summary before accepting.

Secrets go out encrypted — with a key that lives in the source

Provider API keys, database connection passwords, the SMTP password, webhook tokens and the environment variables all leave encrypted in the file. But the default key is in the source code: that protects against casual reading by whoever opens the JSON, not against someone determined.

For the file to be genuinely confidential, set the PRO_AI_EXPORT_SECRET environment variable on both installations. With it, the file only opens where the same value is configured — and a file with the wrong key is refused with a clear message, instead of writing rubbish where the password should be.

Either way: the export file is sensitive material. Store it as such and delete it once you have imported.
